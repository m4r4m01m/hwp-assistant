# HWP Assistant 작업 맥락과 GPT 인수인계 프롬프트

아래 내용을 HWP Assistant 프로젝트의 현재 맥락으로 받아들여 줘. 나는 Codex로 구현을 진행하고 있으며, 너에게는 설계 검토, 남은 작업의 우선순위 판단, 다음 Codex 작업 지시문 작성을 부탁하려고 한다. 기존 구현을 출발점으로 삼고, 요구사항과 구현 상태와 실행 검증 결과를 구분해 줘.

Git 상태는 2026년 10월 6일에 원격 조회로 확인했다. 제품 시험 결과는 별도 표시가 없는 한 저장소에 남은 2026년 9월 27일 기록이다. 이번 Git 확인에서 제품 시험을 다시 실행한 것은 아니다.

## 프로젝트 목적과 작업 환경

회사에서 한컴오피스 한글로 작성하는 문서를 웹에서 안전하게 이어서 편집하고, AI가 문단 수정안을 제안하면 사람이 비교하고 승인해 저장하는 서비스다. HWPX 문서함, 버전 관리, 문서별 대화와 작성 기준, 양식 재사용을 함께 제공한다. 개발은 공중망에서 진행하고 이후 사내 망분리 환경으로 이식할 수 있도록 만드는 것이 목표다.

- 저장소: https://github.com/m4r4m01m/hwp-assistant
- 로컬 작업 경로: `<LOCAL_PATH>`
- 백엔드: `backend/app`의 FastAPI, SQLAlchemy, 파일 저장소, `LlmProvider`.
- 프런트엔드: `frontend/src`의 React, TypeScript, `EditorAdapter`.
- 편집기: 자체 호스팅한 rhwp 0.8.6. 기준 커밋은 `e8800c8def63449808a4092798442652ed460552`이고 고정값은 `scripts/engine-lock.json`에 있다.
- 로컬 DB는 SQLite다. PostgreSQL과 Docker Compose 구성은 있지만 실제 실행 검증과 구분해야 한다.
- 신규 유료 API나 유료 인프라를 기본안으로 추가하지 않는다. AI 오류를 유료 API 호출로 자동 대체하지 않는다.

## 이번 Git 비교 결과

`git fetch origin --prune`를 실행하고 `git ls-remote --heads origin`으로 원격 브랜치 목록도 직접 확인했다. 원격에는 다음 두 브랜치가 있다.

| 비교 대상 | 커밋 | 확인 결과 |
|---|---|---|
| 로컬 `main`과 `origin/main` | `1e0538781e02ac85d095bb3c72bf844943c305b3` | 동일. 로컬 전용 0개, 원격 전용 0개 커밋 |
| `origin/codex/initial-implementation` | `2dbfd6084ad59a7fb2472228a04b6b416026ed39` | 이미 `main`의 조상. 브랜치 전용 미반영 커밋 0개 |

`main`의 최신 커밋은 2026년 9월 27일의 `Merge PR #19: HWP Assistant implementation and README`다. 구현 브랜치와 `main`은 파일 내용도 동일하며, `main`에 병합 커밋 하나가 더 있다. 따라서 이번 확인에서는 새 브랜치나 추가로 병합할 변경이 없었다. 이미 반영된 구현을 다시 병합하거나 코드가 새로 반영됐다고 표현하지 않는다.

작업 시작 시 추적 파일 수정과 미추적 파일은 없었다. 이번 작업은 이 인수인계 문서만 추가했으며 제품 코드 변경, 추가 병합, 커밋, 원격 푸시는 하지 않았다.

주요 이력은 기존 계획과 LM Studio PoC 보존 → `03fe04b`에서 HWPX 편집·Codex 승인 수정·검증 구현 → `2dbfd60`에서 README 정리 → [PR #19](https://github.com/m4r4m01m/hwp-assistant/pull/19) 병합이다.

## 반드시 유지할 원칙

1. HWPX가 원본이다. 최초 업로드와 과거 버전 blob을 수정하지 않는다. 과거 버전 복원도 새 버전을 만든다.
2. 파일 영속화와 DB commit이 확인된 뒤에만 저장 완료라고 표시한다. export나 다운로드 성공은 서버 저장 성공이 아니다.
3. 문서 행 잠금 안에서 권한, 편집 임대, 기준 버전을 검사하고 새 버전을 하나의 트랜잭션으로 게시한다. SQLite의 개발용 쓰기 직렬화와 PostgreSQL의 실제 행 잠금 검증을 구분한다.
4. AI는 후보를 만들고 사용자가 승인한다. 승인된 텍스트만 rhwp exact command로 적용하며 문서, 선택 위치, 원문, 서식, 주변 문맥, 편집 리비전을 다시 검사한다. AI가 HWPX 전체 XML을 재작성하게 하지 않는다.
5. 사용자 수정사항, 열린 문서의 미저장 내용, 기존 DB와 파일을 보존한다. checkout을 reset/clean하거나 진단 엔진으로 실행 중인 기본 엔진을 조용히 덮어쓰지 않는다.
6. `docs/internal-doc-assistant-plan-v0.4.md`는 요구사항 기준선이다. 완료 보고로 고치거나 미구현 요구사항을 삭제하지 않는다.
7. 실제 엔진 시험, 고정 응답을 쓰는 mock AI 시험, 실제 모델 호출, 한컴 UI 왕복, 인터넷 차단 환경 시험을 각각 구분한다.

## 현재 구현된 기능

- HWPX 업로드와 새 문서 생성, 본문·표 수동 편집, 저장·자동 저장·다른 이름으로 저장, 새 버전 업로드, 버전 다운로드·복원.
- 편집 임대와 기준 버전 검사, 변경분 저장, 멱등 요청, 충돌 시 미저장 내용과 복구 다운로드 보존. 자동 병합은 없다.
- owner/editor/reader 문서 권한과 문서별 대화. 문서 권한자는 작성자와 관계없이 대화·미적용 후보·적용 이력을 읽을 수 있다. reader는 승인·적용·저장할 수 없다. 공유 문서 안의 작성자 전용 비공개 대화는 현재 정책이 아니다.
- 작성 목적, 확정 사실, 작성 기준, 선택 문단 등 자체 컨텍스트를 문서 기준 버전과 함께 저장.
- 실제 Codex와 문서 MCP를 사용하는 후보 2개 생성, AS-IS와 TO-BE 비교, 사용자 승인, rhwp 적용, 서버 저장, 이력 연결.
- HWPX 양식 등록, 메타데이터 추천, 고정된 양식 버전으로 새 문서 생성. 기존 문서에 양식 블록을 삽입하거나 변수를 치환하는 기능은 후속 범위다.

AI 수정 흐름은 요청 순간의 미저장 선택 문단을 스냅샷으로 고정 → 후보 2개 생성 → 사용자 비교·승인 → 원문과 편집 상태 재검사 → rhwp 명령 적용 → 새 HWPX 버전과 적용 이력 확정이다. 비교 중 자동 저장을 보류하며, 원문이나 기준 버전이 바뀌면 강제로 적용하지 않는다. 작업 ID, 후보 ID, 승인, 적용 영수증, 저장 버전의 연결을 남긴다.

안전 AI 적용 범위는 본문의 단일 서식 문단이다. 표 셀, 필드, 컨트롤, 혼합 글자 서식 문단까지 자동 수정할 수 있다고 확대해서 설명하지 않는다. 표 셀의 수동 편집 지원과 AI 자동 적용 지원은 별개다.

## AI 연결 방식

Codex 경로는 서버와 같은 OS 사용자의 설치된 Codex CLI와 기존 ChatGPT 로그인, 작업 전용 MCP를 사용한다. `HWP_CODEX_USER`로 지정한 앱 사용자만 이 실행 경로를 사용할 수 있으며 다른 문서 권한자에게 서버 소유자의 Codex 실행 권한을 자동 부여하지 않는다. 실행기는 제한된 임시 환경에서 `read_rewrite_task`, `submit_rewrite_candidates`만 허용한다. 후보 생성 권한으로 승인이나 저장을 수행할 수 없다.

로컬·사내 모델 경로는 `LlmProvider`와 OpenAI 호환 API를 사용하며 `LLM_PROVIDER`, `LLM_BASE_URL`, `LLM_MODEL` 등으로 설정한다. LM Studio PoC는 보존돼 있다. 이전 계획에 있는 Ollama를 필수로 다시 도입할 필요는 없다. 운영 예정 명칭인 “Qwen 3.8”의 정확한 모델 ID, 크기, API 규격은 미확인이다. Qwen3-8B 같은 다른 이름으로 임의 치환하지 않는다. 9월 27일에는 로컬 `127.0.0.1:1234/v1/models`가 연결 거부였으며 사내 모델 성공을 입증한 기록은 없다.

현재 구현 밖에는 폴더·이동·휴지통 등 전체 드라이브 기능, 공개 링크 공유, 양식 기반 AI 초안, 코드 규칙 검사, 양식 블록 삽입·변수 치환, SSO, 실시간 공동 편집이 있다. 브라우저 강제 종료 후 저장 재시도 큐 복원, 서버 종료로 중단된 AI 작업 자동 재개도 지원하지 않는다.

## 재개할 때 참고할 실행 조건

기본 설치 안내는 README에 있다. 백엔드 의존성은 `backend/requirements.lock.txt`, MCP 의존성은 `backend/requirements-mcp.lock.txt`, 프런트엔드는 `frontend/package-lock.json`에 고정한다. `npm ci`만으로 수정 편집기 엔진이 만들어지지는 않는다.

일반 회귀 명령은 루트의 `.venv/Scripts/python -m pytest -q`, frontend의 `npm exec tsc -- --noEmit`, `npm run test:engine-build`, `npm run test:e2e`다. E2E에는 실행 중인 API와 엔진을 제공하는 웹 서버가 필요하다. 인증 시나리오는 별도 인증 시험 서버와 `HWP_E2E_AUTH_URL`이 있어야 하며, 설정이 없어서 skip된 시험을 통과 수에 포함하지 않는다. MCP 의존성이 없을 때의 skip도 구분한다.

기본 `npm run build`는 검증된 최적화 코어를 요구하고 진단 산출물을 거부한다. Docker를 보류한 상태에서 재현할 때는 `docs/engine-empty-fill-fix.md`의 명시적 Windows 진단 빌드와 별도 출력 경로를 사용한다. 과거 기록의 서버 포트·PID·브라우저 창이 지금도 살아 있다고 가정하지 말고 현재 상태를 확인한다. 이번 Git 점검은 실행 중인 서버와 엔진 배포 상태를 갱신한 작업이 아니다.

위 맥락을 바탕으로 다음 대화를 이어가 줘. 첫 답변에서는 현재 기능, 실제 확인된 품질, 미검증·보류 항목을 짧게 정리하고 Docker 보류를 유지한 다음 작업 후보를 우선순위 3개로 제안해 줘. 각 후보에는 해결할 문제, 가장 작은 변경 범위, 완료를 판정할 검증을 적어 줘. 이어서 가장 우선할 후보 하나를 Codex에 바로 전달할 수 있는 구체적인 작업 프롬프트로 작성해 줘.

새 일정·공수·모델 성능 수치를 근거 없이 만들지 말고, 이미 구현된 기능을 처음부터 다시 만들도록 지시하지 말아 줘. 저장소나 실행 환경에 직접 접근할 수 없다면 이 인수인계에 기초한 판단임을 밝히고, 필요한 파일·실행 증거만 구체적으로 요청해 줘. 계획을 세운 사실과 코드를 반영한 사실, 테스트를 통과한 사실을 분리해 설명해 줘.
