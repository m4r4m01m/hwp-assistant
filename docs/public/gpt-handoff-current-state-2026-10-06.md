# HWP Assistant 현재 상태와 GPT 후속 검토 프롬프트

아래를 이전 HWP Assistant 대화에 이어 붙여 줘. 2026년 10월 6일의 현재 로컬 상태다. 이미 끝난 구현, 과거 검증, 새로 재현했지만 아직 수정하지 않은 경계를 구분해 다음 작업 지시를 작성해 줘. 원격 main에는 아래 미커밋 변경이 없다는 점을 전제로 판단해 줘.

## 먼저 바로잡을 AI 역할

내가 기대한 기본 방향은 **Codex가 LLM 역할을 맡아 문서 후보를 생성하는 것**이다. 별도 로컬 모델 설치나 가동이 현재 개발의 필수 조건이라는 뜻이 아니다.

- 기존 앱은 설치된 Codex CLI와 기존 ChatGPT 로그인, 작업 전용 MCP로 후보를 생성한다. 앱 요청으로 별도의 제한된 Codex 실행을 시작하며, 지금 개발 중인 이 채팅 전체를 제품에 자동 전달하는 구조는 아니다.
- 앞서 GPT가 준 지시가 “로컬·사내 OpenAI 호환 모델도 기존 후보 2개 흐름을 사용하도록 확장”이었기 때문에 선택 경로를 추가했다. Codex를 없애거나 로컬 모델로 기본값을 바꾸지 않았다.
- `HWP_REWRITE_PROVIDER`는 미설정 시 `codex`, 별도 서버를 쓰려는 경우만 `llm`이다. 로컬 모델은 LM Studio나 사내 OpenAI 호환 서버에서 따로 실행하는 모델을 말한다. 실제 모델을 설치·다운로드·호출하지 않았다.
- 앞으로 Codex 중심 사용을 기본으로 설명해 줘. “로컬 모델 서버가 없으므로 프로젝트 전체가 막혔다”고 해석하지 마라. 로컬 경로의 실호출 검증이 남았다는 뜻이다. 이미 추가한 선택 경로를 임의로 삭제하거나 새 모델을 도입하지 마라.

## 프로젝트와 보존 원칙

회사 한글 문서를 웹에서 편집하고, AI 후보를 사람이 비교·승인한 뒤 새 버전으로 저장하는 HWP Assistant다. FastAPI·SQLAlchemy·파일 저장소와 React·TypeScript·EditorAdapter를 사용한다. HWPX 문서함, 수동 본문/표 편집, 저장·자동 저장·버전 다운로드/복원, 문서 권한·대화·컨텍스트 보관, 양식 등록·추천·새 문서 복사는 기존 구현이다.

- 저장소: `m4r4m01m/hwp-assistant`.
- 로컬: `<LOCAL_PATH>`.
- 현재 확인한 HEAD: `main`, `1e0538781e02ac85d095bb3c72bf844943c305b3`.
- 앞선 원격 재조회에서는 `main`과 `codex/initial-implementation`만 있었고, 구현 브랜치는 PR #19로 병합되어 트리가 같았다. 추가 반영할 원격 코드는 없었다. 이번 안전 경계 점검에서는 원격을 다시 조회하지 않았다.
- 10월 6일 후속 구현은 **미커밋·미푸시 상태**다. 새 `backend/tests/test_rewrite_boundaries.py`도 미추적이다. HEAD만으로 현재 소스를 식별할 수 없다.
- HWPX가 원본이며 최초·과거 blob은 불변이다. 복원도 새 버전을 만든다. 파일 영속화와 DB commit 확인 후에만 저장 완료다.
- 권한·임대·기준 버전을 검사한 트랜잭션으로 게시한다. 승인된 텍스트만 rhwp exact command와 원문·서식·인접 문맥·문서/선택/리비전 보호를 거쳐 적용한다.
- 사용자 변경과 미저장 버퍼, 기존 DB, 인증 설정, 기본 엔진을 보존한다. reset/clean, 자동 병합·재실행, 유료 AI 대체, 모델 다운로드, 무단 커밋·푸시·병합은 제외한다.
- Docker·PostgreSQL·nginx 배포는 이번 범위 밖이다. `docs/internal-doc-assistant-plan-v0.4.md`는 요구사항 기준선이며 완료 보고로 바꾸지 않는다. 기존 인수인계와 날짜별 증거도 덮어쓰지 않는다.

## 2시간 작업에서 구현하고 검증한 내용

기존 “미저장 문단 스냅샷 → 후보 2개 → 사용자 승인 → rhwp 적용 → 영수증 → 서버 저장 → 이력”을 재사용했다. 새 편집기·DB 마이그레이션·AI 프레임워크는 추가하지 않았다.

1. `LlmProvider.rewrite`, 로컬 실행기, 공통 후보 계약·게시 검사를 추가했다. Codex 경로와 `HWP_CODEX_USER` 제한은 유지한다. 로컬 경로도 문서 editor/owner, 본인 임대, 기준 버전을 확인한다. 일반 사용자가 후보 등록 API로 결과를 주입할 수 없다.
2. 요청 순간의 원문·지시와 로컬 제공자 설정을 고정한다. 모델 네트워크 호출 중 DB 쓰기 트랜잭션을 잡지 않고, 호출 전후 상태를 확인한다. 유효 후보 2개와 ready를 함께 commit하며 생성만으로 버전/Application을 만들지 않는다.
3. 후보 수·길이·공백·중복·필드·JSON을 엄격히 검사한다. 고정 엔진 한도는 단일 본문 문단, 최대 4,000 Unicode 코드포인트, 줄바꿈/탭 금지다. JSON schema 지원을 추측하지 않는다. 입력에 없는 사실을 만들지 말라는 지시는 사실성 보장이 아니다.
4. 생성 요청 응답 유실은 동일 ID·원문·지시로 재확인한다. 승인 저장 commit 후 응답 유실은 같은 출력·영수증·저장 키로 재시도한다. 승인/영수증 응답 유실과 후속 입력 보존도 시험했다.
5. 논리적 결과 수신 중단과 600초 만료 표시를 추가했다. 이미 시작한 HTTP/CLI의 물리적 종료와 다르며, 서버 재시작 후 자동 재실행하지 않는다.
6. 실제 rhwp에서 제목·본문·2×2 표의 저장/다운로드/재업로드/재열기 3회와 새 버전 복원을 시험했다. 읽기 전용 SQLite/blob 감사와 분리 시험 실행기도 추가했다.

**현재 두 후보 입력은 선택 문단과 개선 지시뿐이다. `context_used=false`다.** 목적·사용자 확인 사실·작성 기준·전체 대화를 후보 생성에 전달했다고 표시하지 않는다. DB 보관과 새 세션의 입력 재구성, 실제 모델 후속 생성은 서로 다른 완료 조건이다.

또한 후보가 4,000자 이내여도 적용으로 **페이지 수가 바뀌면 엔진이 거부**한다. 엔진 단독 시험에서는 원문과 내보내기 바이트가 복구됨을 확인했다. 이를 이유로 보호를 끄거나 후보를 자동 축약하지 않는다.

## 방금 시작한 안전 경계 점검에서 재현한 3개 항목

새 파일 `backend/tests/test_rewrite_boundaries.py`를 추가하고 아래 명령을 실행했다.

```powershell
.venv/Scripts/python -m pytest -q backend/tests/test_rewrite_boundaries.py
```

결과는 **3 failed, 기존 경고 1개**다. 실패를 숨기거나 xfail로 바꾸지 않았다. **아직 제품 소스 수정은 하지 않았다.** 이번 재현은 모의 실행기/CLI와 합성 DB를 사용하며 실제 모델 호출이 아니다.

1. `test_cancel_and_reissue_keeps_physical_execution_capacity_until_worker_returns`
   - 모의 스레드를 완료시키지 않은 채 작업 접수→논리적 중단을 반복했다.
   - 시험에서 정한 “동시에 2개까지, 다음 접수는 429”라는 기대와 달리 세 번째도 접수됐다. 현재 구현에는 실행 상한이 없다.
   - **2라는 상한은 기존 제품 사양이 아니라 재현 시험의 제안값**이다. 실제 서버를 폭주시킨 시험은 아니다. 작은 동시 실행 상한과 물리적 실행 종료까지 슬롯을 유지하는 최소 방식을 검토하되 새 큐 프레임워크나 자동 재실행은 추가하지 마라.
2. `test_codex_dispatch_freezes_model_and_endpoint_at_task_acceptance`
   - 접수 뒤 모의 Codex 설정을 `accepted-model`에서 `later-model`로 바꾼 뒤 실행했다.
   - 실행 근거에서 `later-model`이 관찰되어 접수 시 설정 고정 기대에 실패했다. 현재 Codex 실행기는 worker에서 설정을 읽는다. 로컬 경로의 제공자 인스턴스 고정과 구분해야 한다.
   - 모델 assertion에서 먼저 실패했으므로 뒤의 endpoint assertion까지 통과했다고 하지 마라. 엔드포인트도 worker 시점에 읽는 코드이므로 함께 확인할 대상이다.
3. `test_publication_lock_refreshes_preloaded_task_and_document`
   - 한 SQLAlchemy Session에 문서와 작업을 미리 읽어 두고, 다른 트랜잭션에서 임대 토큰을 바꿨다.
   - `lock_task`가 작업은 refresh하지만 이미 로드된 문서 객체는 이전 토큰을 유지해 실패했다.
   - 현재 실행기는 게시 단계마다 새 Session을 쓰므로, 이것만으로 현재 정상 경로에서 실제 잘못된 게시가 발생했다고 단정하지 마라. 재사용 Session에서의 helper 경계 누락을 재현한 것이다.

원본 실패 로그에는 합성 시험의 임대 토큰이 출력될 수 있으므로 공유 자료에는 원문 로그를 넣지 않는다. 비민감 요약과 시험 소스로 재현한다.

## 아직 끝나지 않은 안전 경계 요청

앞서 요청한 A~D 작업 전체가 끝난 상태가 아니다. 기존 시험과 연결할 부분은 중복 구현하지 않고, 남은 조건만 장벽·이벤트로 재현해야 한다. 긴 대기를 기본 시험에 추가하지 마라.

- **A 게시 경쟁:** 중단 commit 뒤 응답, 게시 성공 뒤 중단/예외, 권한 회수 후 재부여, 임대 반납/재발급과 정상 갱신, 최신 ORM 상태 확인. 기존에 중단 뒤 응답·완료 후 중단 거부·권한 회수·기준/임대/만료 검사가 있으나 A 전체 연결표와 추가 장벽 시험은 아직 작성하지 않았다.
- **B 페이지 수 거부 뒤 제품 복구:** 승인 기록은 생기고 영수증은 없는 실제 UI 상태에서, 원문/비대상 편집/출력 바이트·버전 수를 확인하고 오류 표시·비교 종료·수동 저장·새 작업 재개를 시험해야 한다. 엔진 단독 rollback 통과가 이 제품 흐름 전체의 통과는 아니다.
- **C 재시도 상태 분리:** 중단/새 지시가 미해결 승인 출력·키를 버리지 않는지, commit 응답 유실과 추가 입력이 겹칠 때 각각 보존되는지, 문서 A의 늦은 응답이 B를 바꾸지 않는지, 재시도에서도 현재 권한을 확인하는지 마감해야 한다. 기존 응답 유실 시험과 중복하지 않게 조합한다.
- **D 자원/설정:** 논리 중단과 물리 종료를 구분하고, 실제 실행 종료 전 슬롯 반환 여부·설정 고정·같은 ID의 다른 모델 재호출 방지를 확인한다. 위 신규 실패 1·2가 관련된다.

소스 수정이 끝나면 **같은 최종 변경셋**에서 전체 pytest, TypeScript, 엔진 빌드 보호, 인증 포함 일반 E2E를 실행해야 한다. 현재 이 일괄 회귀는 미실행이다. 진단 번들은 현재 소스로 새로 만들고 연결해야 한다. 기존 1시간/602초 결과는 역사적 근거이며 관련 로직을 바꾸면 재검증 대상을 명시해야 한다.

컨텍스트 확장은 이번에는 **설계만** 요청했다. 목적·사용자 확인 사실·작성 기준부터 시작하고, 전체 대화 자동 투입은 제외한다. 컨텍스트 ID/리비전/문서 기준/실제 값/출처/입력 해시의 고정 위치, 충돌·오래된 기준 처리, AI 과거 답변과 사용자 확인 사실 구분을 설계해야 한다. 아직 설계 문서도 작성하지 않았다. 구현 없이 `context_used=true`로 바꾸지 마라.
