# 블록 삽입의 기존 본문 배치 보호

## 확인한 결함과 적용 범위

고정 엔진 rhwp `e8800c8def63449808a4092798442652ed460552`에서 아래 순서만으로 기존 본문의 줄바꿈과 단어 간격이 바뀌는 것을 실제 WASM으로 재현했다.

1. `HwpDocument.createEmpty()` 후 `createBlankDocument()`를 호출한다.
2. 첫 문단에 `insertText()`로 `\n`을 포함한 세 줄을 넣는다.
3. `getPageTextLayout()`로 현재 줄과 글자 좌표를 읽는다.
4. `exportHwpx()` 결과를 새로운 `HwpDocument`에 넣고 같은 좌표를 읽는다.

테스트 문서의 텍스트와 기존 서식은 보존됐지만 3줄이 5줄로 바뀌었다. 블록 API 없이 재현되므로, 이 차이를 서버의 블록 스타일 병합이나 CSS 변경에 귀속하지 않는다. HWPX를 먼저 연 뒤 편집하는 경로에서도 원래 문서 형식과 새로 계산된 문단의 문자 위치 축이 섞이는 현상을 재현했다.

upstream의 기존 회귀시험 `issue_5943_hwpx_lineseg_axis_rebase.rs`와 `issue_5961_hwpx_lineseg_axis_projection.rs`에는 서로 다른 Hancom 실측에 따른 첫 문단의 `secPr`/`colPr` 문자 위치 규칙이 있다. 현재 환경에서 둘을 포괄하는 변환 규칙을 검증하지 못했으므로, parser에 일괄 16칸 보정을 넣거나 저장된 모든 `lineSeg`를 없애지 않는다. 원래 양쪽 정렬, 원본과 이력 파일, 내용·서식·자원 검증도 그대로 유지한다.

이번 변경은 **의도하지 않은 기존 본문 배치를 적용하기 전에 거부하는 보호 장치**다. 엔진의 HWPX 변환 결함 자체를 해결했다는 의미는 아니다.

## 검사 방식

`scripts/assistant-bridge.ts.txt`의 `bodyLayoutEvidence()`는 보이는 편집기와 같은 native 문서에서 다음 정보를 읽는다.

- 문서 epoch, 편집 revision, export SHA-256
- 구역별 본문 문단 수, 각 문단의 전체 텍스트 SHA-256와 문자 수
- 실제 본문 줄의 논리적 시작·끝 위치와 각 글자의 x 좌표·advance

빈 본문 문단도 포함한다. 표 셀과 글상자의 별도 좌표 경로는 이 본문 검사에 포함하지 않는다. 기존 서버의 내용·서식·자원 보존 검사는 계속 별도로 수행한다.

프런트엔드는 서버의 `plan.insert_after`와 `plan.top_level_count`로 삽입 전후 문단 인덱스를 대응시킨다. 기존 문단의 텍스트와 줄 경계가 같아야 하고, 줄 안의 상대 x 좌표와 글자 advance 차이는 0.75px 이하여야 한다. native API의 좌표 정밀도는 0.1px이다. 페이지 번호와 y 좌표는 비교하지 않아, 블록이 추가되어 뒤의 문단이 다른 쪽으로 이동하는 정상적인 재배치를 허용한다.

입력 capture, staging preview, 적용 직전의 문서/바이트 fence와 함께 검사한다. 좌표가 달라지거나 읽기 자체를 안전하게 완료하지 못하면 staging을 적용하지 않고 기존 편집기를 유지한다. 이전 엔진 bundle에 새 bridge 메서드가 없는 경우에도 원문을 유지하며, 현재 내용을 저장하거나 복구용으로 내려받은 뒤 페이지를 다시 열고 문제가 계속되면 관리자에게 문의하도록 안내한다. 관리자는 새 bridge를 포함한 검증된 엔진 bundle을 함께 제공해야 한다.

## 비용과 한계

키 입력이나 자동 저장마다 실행하는 검사가 아니다. 블록 준비와 적용이라는 명시적 작업에서만 실행한다.

검사 한도는 200쪽, 본문 10,000문단, 본문 200,000자 및 렌더 glyph 200,000개다. native 호출 사이에서 4초 경과를 검사하며, 이미 시작한 단일 native 페이지 호출을 중간에 취소할 수는 없다. 한도나 시간 초과는 배치 결함 판정과 구분해 안내한다.

이 보호 장치는 본문의 줄 경계와 가로 글자 배치를 비교한다. 표·글상자 내부 배치, 그림, 세로 배치의 완전한 시각적 동일성이나 Hancom 앱에서의 렌더링까지 보장하지 않는다. 이미 달라진 상태로 로드된 문서를 과거의 정상 화면으로 복구하지도 않는다. 원래 변환 결함은 별도의 엔진 수정과 Hancom 검증이 필요하다.

## 실제 엔진 회귀검사

```sh
node scripts/test-engine-block-layout.mjs PATH_TO_VERIFIED_CORE_PKG
```

이 검사는 실제 WASM으로 새 문서 작성, HWPX export/import, 페이지 나누기와 글자 좌표 조회를 수행한다. Studio host의 얇은 연결부만 VM에 공급하고, 실제 bridge 코드와 프런트엔드 비교 함수를 함께 실행한다.

검사 내용은 다음과 같다.

- 정상 블록 추가 후 기존 문단과 빈 문단의 인덱스 대응 및 글자 배치 유지
- 여러 쪽 문서가 5쪽에서 6쪽으로 늘어나는 실제 페이지 이동 허용
- 알려진 첫 문단 round-trip 왜곡을 텍스트 해시가 같아도 거부
- 읽기 전후 export SHA-256 불변
- 페이지 수 한도를 초과한 조회 거부

이 검사는 `scripts/build-engine.mjs`에서 기존 실제 WASM fill/selection 검사와 함께, Studio 출력 생성 전에 실행된다. native diagnostic bundle과 Docker 최적화 release bundle의 구분 및 기존 provenance 검증은 변경하지 않는다. native 빌드 결과를 Docker release 검증 통과로 기록하지 않는다.

`frontend/tests/block-insert.spec.ts`에도 실제 Studio/Chromium과 임시 API를 사용하는 회귀를 추가했다. 엔진이 만든 빈 HWPX를 정상 업로드 경로로 열고 첫 문단을 세 줄로 편집한 뒤, 둘째 문단 뒤 블록을 요청한다. 서버가 정상 블록 미리보기를 반환해도 기존 첫 문단의 렌더링이 달라지면 적용 버튼을 내보내지 않고 staging을 정리하는지 확인한다. 원래 iframe, 미저장 export 바이트, 문단 좌표, 원본 파일 및 서버 버전 목록이 모두 그대로여야 한다. 이 경로는 LLM을 호출하거나 렌더 좌표를 모의하지 않는다.
