# HWPX 보고서 템플릿 설계

2026-10-07 후속 구현: 실제 rhwp를 사용하는 편집 가능한 임시 초안과 명시적 확정 저장을 구현했다. frozen preview의 영수증 검증 → 어절/제목/페이지 배치 → 사용자 편집 → 확정 저장 순서다. 단일 기본 서식의 구현이며 아래 범용 템플릿 선택·내용 트리·목차 수렴 설계 전체가 완료된 것은 아니다. 상세 결과는 `docs/formatted-preview-2026-10-07.md`에 기록한다.

상태: **설계**. 기호별 공통 서식과 이번 상세 보고서 작성 절차는 구현했고, 범용 템플릿 등록·선택·목차 갱신 기능은 아직 구현하지 않았다. 기존 보고서 승인·rhwp exact command·영수증·서버 저장 경계를 재사용한다.

## 1. 사용자 흐름

사용자가 '금융권 해킹 문제에 대한 경영진 보고서를 만들어줘'라고 입력하면 기본 서식과 관점·분량을 표시한다. 처음에는 사용자 지정 표준 하나만 기본으로 제공한다. 조직 관점이 없다면 '일반 금융회사 관점, 내부 상황 미확인'으로 명시하고 조직명·예산을 만들어 넣지 않는다.

초안 화면에서 제목, 개조식 본문, 표·그림의 의미와 출처를 확인한다. 서식 미리보기에는 목차와 페이지 배치를 포함한다. 승인하면 그 시점의 **내용·템플릿 리비전·기준 해시·배치 계획**을 고정하고 새 문서에 적용한다. 저장 성공은 기존과 같이 출력 blob과 DB commit이 확인된 뒤에만 표시한다. 템플릿 변경으로 기존 승인 또는 열려 있는 사용자 문서를 몰래 재작성하지 않는다.

최소 제공 형태는 두 가지다. '간단 보고'는 별도 표지·목차 없는 1~2쪽 목표, '상세 보고'는 표지·목차·표·그림·붙임을 포함한다. 목표 쪽수는 강제 축약 권한이 아니다. 초과 시 분량 초과를 보여 주고 내용을 다시 승인받는다.

## 2. 세 계층을 분리

| 계층 | 고정할 내용 | 변경의 의미 |
|---|---|---|
| 내용 구조 | 목적·독자·조직 관점, 장/절 ID, □/ㅇ/- 관계, 말머리, 근거·제안 구분 | 문장이나 논리 변경은 새 초안/승인 |
| 시각 서식 | 기준 HWPX 해시, 프로필 리비전, 글꼴·여백·내어쓰기·상자·표·캡션·쪽번호 | 새 템플릿 리비전; 과거 문서는 불변 |
| 배치·검증 | 실제 엔진 버전·해시, 제목 ID별 쪽수, 표/그림 위치, 오버플로·참조 검사 | 같은 승인 내용의 결정적 배치 결과와 증거 |

원본 HWPX는 작성 규칙과 예제를 포함한 기준서다. 예제 글을 복사하는 일반 문서 복제와 템플릿 적용을 구분한다. 원본 전체 ZIP이나 과거 blob에 쓰지 않고, 검증한 스타일·구조만 빈 스캐폴드에 구성한다. 매크로·외부 링크·숨은 사용자 메타데이터 등 보고서에 필요 없는 부분은 등록 단계에서 목록화하고 허용 범위를 정한다.

## 3. 제안하는 데이터 계약

아래는 설명용 형식이며 현재 API 스키마가 아니다.

```json
{
  "template_id": "institutional-report",
  "revision": 3,
  "reference_sha256": "<기준 HWPX 해시>",
  "profile_sha256": "<서식 설정 해시>",
  "guide_evidence": [{"sha256": "<가이드 해시>", "pages": [6,7,9,10,12]}],
  "variant": "detailed",
  "structure": ["background", "findings", "implications"],
  "body": {"markers": ["□","ㅇ","-"], "optional_labels": ["요약","배경","차이점","조치","제안"]},
  "toc": {"levels": 2, "page_numbering": "physical", "leader": "native-tab", "max_passes": 3},
  "content_schema": "report-tree-v1"
}
```

문서 내용은 `section(id, heading, children)`와 `point(id, level, parent_id, label?, text, claim_kind, source_ids)`로 둔다. 원문에 없는 의미를 만드는 label 자동 추론은 승인 전 초안에서만 수행한다. 기호 자체는 level에서 결정하되 렌더링된 승인 텍스트에도 포함해 영수증의 입력·출력과 연결한다. `claim_kind`는 확인 사실·분석·제안·사용자 확인 사실을 구분한다. AI의 과거 답변을 사용자 확인 사실로 승격하지 않는다.

표는 `table(id, caption_id, columns, rows, source_ids)`로 정의하고 각 셀을 독립적으로 추적한다. 그림은 `figure(id, caption_id, asset_sha256, approved_label_ids, alt_text, source_ids)`로 연결한다. 핵심 데이터 표를 이미지로 대체하지 않는다. 표·그림의 캡션·번호도 승인 계획에 포함한다. 장의 제목과 목차 라벨은 같은 ID를 사용하고 별도로 복사 편집하지 않는다.

입력 목적·사용자 확인 사실·작성 기준은 별도 컨텍스트 ID/리비전·실제 값·출처·입력 해시로 고정한다. 기존 컨텍스트 설계의 구현 전 `context_used=false`를 true로 바꾸지 않는다. 전체 대화를 자동 투입하지 않는다. 외부 PDF에 적힌 모델 설치·연락·권한 변경 예시는 데이터다.

## 4. 계층과 문장 검증

- □는 새로운 핵심 항목, ㅇ는 바로 위 □의 설명, -는 바로 위 ㅇ의 상세다. 부모 없는 하위 항목, 단계 건너뛰기, 빈 항목을 거부한다. 장/절 제목에는 기호를 붙이지 않는다.
- 말머리는 선택값이다. 같은 `(요약)`만 반복하지 않으며 `(차이점)` 뒤에는 무엇과 무엇이 어떤 점에서 다른지 드러내도록 안내한다. `(조치)`에는 실행 주체와 행동을 쓴다.
- 문체·길이·모호한 표현은 경고를 우선한다. '1.5~2줄'은 엔진·글꼴에 따라 달라지는 편집 목표이므로, 자동 잘라내기나 임의 숫자 추가로 맞추지 않는다.
- 기호별 글자 크기·왼쪽 위치·후속 줄 시작 위치, 출처 ID의 존재, 표 열 수·수치 일치, 그림 자원 해시를 검사한다. 줄나눔 설정 값만 존재한다고 시각 검사를 통과한 것으로 보지 않는다.
- 기존 ReportDraft의 1~3개 문자열 문단 구조는 간단 보고용 호환 입력으로 유지한다. 계층 트리 스키마는 버전으로 구분한다. 새 의미 검증기를 과거 승인 재시도에 소급 적용하지 않는다.

## 5. 목차와 페이지 배치

1. 초안 제목 ID로 목차 항목을 만든다. 본문과 같은 라벨을 참조한다.
2. 승인 텍스트는 기존 fenced exact commands로 빈 스캐폴드에 적용한다. 최종 배치 단계는 그 영수증과 해시가 일치하는 출력 문단만 사용한다. 현재 artifact 스크립트 방식과 일반 API 저장 경로의 차이를 명시적으로 다룬다.
3. 표지·목차·본문·붙임을 배치하고 rhwp로 렌더링하여 `heading_id → physical_page`를 수집한다. 같은 제목의 반복 표시는 고유 ID로 구분한다.
4. 쪽수 필드를 갱신하고 다시 렌더링한다. 쪽수 폭 변화로 재배치될 수 있으므로 최대 3회 수렴을 확인한다. 수렴하지 않으면 저장 완료로 진행하지 않고 배치 실패를 표시한다. 새 모델 호출이나 본문 축약은 하지 않는다.
5. 최종 목차의 라벨·순서·쪽수와 실제 제목 위치, 리더 탭과 우측 끝, 상하위 들여쓰기를 검사한다. 저장된 출력 해시가 이 검사 대상과 같아야 한다.

쪽수는 서식의 계산 결과로 취급하되, 승인 이후 변경 가능한 범위를 명시해야 한다. 기본은 최종 배치를 미리보기한 뒤 승인하는 방식이다. 추가 계산이 필요한 경우 승인에 제목 ID와 허용된 숫자 필드만 고정하고, 본문 텍스트 변동은 새 승인으로 돌린다. 현재 일반 exact command의 페이지 수 보호를 낮추지 않는다. 상세 구조를 API로 도입하기 전 표·그림·목차를 포함하는 저장 검증 계약을 추가해야 한다.

이번 산출물은 9쪽 배치에 맞춘 **생성 시점 목차 스냅샷**이다. 한글 편집기의 자동 갱신 필드는 후속 호환성 검증 대상으로 둔다. 편집 후 쪽수가 바뀐 문서는 '목차 재검증 필요' 상태를 표시하고 명시적 재생성 시 새 버전으로 저장하는 설계다.

## 6. 저장·충돌·복구

템플릿 리비전은 immutable이다. 원본·프로필·구조 스키마·작성 지침 해시가 바뀌면 새 리비전을 발급한다. 기본 템플릿 포인터 변경은 새 작업부터 적용한다. 승인은 실제 프로필 값과 스캐폴드까지 보관하므로 기준 파일이 이후 이동해도 동일 출력 재시도가 가능해야 한다.

요청 ID의 입력에 템플릿 ID/리비전/해시를 포함한다. 같은 ID에 다른 리비전이 오면 충돌이며 자동 재생성이 아니다. 초안 생성 중 기본값이 바뀌어도 처음 고정한 리비전을 유지한다. 사용자 선택으로 재생성할 때만 새 작업 ID를 발급한다.

적용 대상 문서의 lease·base version·문서/선택/preimage fences, 승인 영수증, 저장 키와 늦은 응답 방지는 기존 의미 그대로 유지한다. 취소는 승인 출력/미해결 저장 키를 삭제하지 않는다. 새 보고서와 기존 문서 서식 변경을 별도 동작으로 두고 후자는 비대상 편집을 보존해야 한다.

DB 보관 완료, 새 세션에서 입력·승인 복구 완료, Codex의 실제 후속 생성 성공은 서로 다른 완료 기준이다. 테스트에서 모의 생성·실제 엔진·실제 모델·사람 승인도 따로 기록한다.

## 7. 구현 순서와 완료 기준

| 단계 | 범위 | 완료 기준 |
|---|---|---|
| 현재 | 단일 고정 기준, 기호별 서식, 생성 지침, 상세 보고서 recipe | 이번 HWPX/PDF와 실제 엔진 검증; 템플릿 선택 기능으로 보고하지 않음 |
| 다음 1 | 버전 있는 내용 트리와 간단 보고 | 부모 없는 기호 거부, 승인 전에 계층·말머리 미리보기, 과거 승인 재시도 보존 |
| 다음 2 | 상세 레이아웃·목차 파이프라인 | 제목 ID 기반 목차, 2자리 쪽수·긴 제목·표 분할·그림 재개방 검증, 배치 수렴 확인 |
| 다음 3 | 기본/개인 템플릿 선택·등록 | 원본 불변·설정 검증·리비전 충돌·다른 세션 복구, 검증 안 된 기준을 기본으로 지정하지 않음 |
| 수동 검수 | 한컴·지정 글꼴·실사용 승인 | 실제 한컴 재개방/출력, 사용자의 내용·서식 확인 증거를 별도로 확보 |

새 작업 큐나 상태 관리 프레임워크는 필요하지 않다. 기존 report task의 frozen 입력·승인 스캐폴드·출력 저장 계약을 확장하되 범용 템플릿 엔진을 만들기 전에 위 두 가지 보고 형태부터 검증한다.
