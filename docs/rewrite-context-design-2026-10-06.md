# 후보 생성 컨텍스트 확장 설계 · 2026-10-06

이 문서는 **설계만** 기록한다. 현재 후보 생성은 선택 문단과 개선 지시만 사용한다. `context_used=false`를 유지했다. 기존 대화 컨텍스트 저장 기능과 새 두 후보 생성 기능의 연결은 구현하지 않았다. 전체 대화 자동 투입, RAG, 새 사실 DB, 새 기능 API, 과거 도구 호출의 자동 재실행은 이번 범위에 없다.

## 첫 입력 범위

첫 범위는 작성 목적, 사용자가 확인해 입력에 포함하기로 한 사실, 작성 기준이다. 선택 메시지 연결은 후속 범위로 둔다. 일반 대화나 AI의 과거 답변은 확인 사실로 자동 승격하지 않는다. “사용자 확인”은 확인 주체와 의사를 기록한다는 뜻이며 외부 사실 검증 완료라는 뜻이 아니다.

| 항목 | 설계할 값 | 현재 구현과의 차이 |
|---|---|---|
| 목적 | 사용자가 확인한 목적 문자열 | 기존 `Context.content.purpose`를 재사용 가능 |
| 확인 사실 | 항목 ID, 실제 문장, 출처, 확인 주체·시각·확인 기록 ID | 기존 `facts`는 문자열이므로 구조화·확인 기록 계약이 필요 |
| 작성 기준 | 문체, 독자, 분량·표현 기준 등 사용자가 지정한 값과 출처 | 기존 `NewContext`에 해당 입력 계약이 없음 |
| 문서 기준 | 문서 ID, 저장 기준 버전, 현재 선택 스냅샷의 문서·텍스트·서식·인접 문맥 해시 | 기존 문서 기준과 exact command fence를 유지 |
| 일반 대화·AI 답변 | 별도의 출처 유형으로만 보관; 기본 입력 제외 | 현재 후보 생성에 대화가 포함되지 않는 상태 유지 |

사실 항목의 출처 유형 예시는 `user_statement`, `document_version`, `user_confirmed_ai_excerpt`다. 마지막 유형도 최초 출처가 AI였음을 남긴다. 사용자가 확인한 실제 문장만 고정하며, 출처를 근거로 메시지 전체를 추가로 가져오지 않는다. 사실·작성 기준 충돌은 사용자에게 명시적으로 정리하도록 요구한다. AI가 어느 쪽이 맞는지 결정하거나 최신 시각만으로 덮어쓰지 않는다.

## 고정 위치와 입력 계약

기존 `conversation_contexts`의 키는 `conversation_id`이고 현재 리비전·기준 버전·JSON 내용·수정 시각을 보관한다. 첫 확장의 논리적 `context_id`는 이 키를 재사용할 수 있다. 현재 테이블은 과거 리비전별 전체 내용을 보관하는 테이블이 아니므로, ID와 리비전만 작업에 넣고 worker가 다시 읽는 설계는 충분하지 않다.

| 데이터 | 제안 저장 위치 | 불변 조건 |
|---|---|---|
| 최신 컨텍스트 ID/리비전/기준 버전 | 기존 `Context` 행 | 문서 잠금 아래 CAS 갱신. 클라이언트 기대 리비전 불일치 시 409 |
| 실제 목적·확인 사실·작성 기준·출처 | `Context.content`의 명시적 버전이 있는 JSON 계약 | 확인 주체·시각은 서버의 현재 사용자로 기록. 클라이언트가 확인자를 임의 지정하지 못함 |
| 작업에 사용한 실제 값 전체 | `RewriteTask.execution` 안의 불변 `context_snapshot` 후보 필드 | 접수 트랜잭션에서 복사. 현재 컨텍스트가 갱신돼도 과거 작업의 값은 변경하지 않음 |
| 컨텍스트 ID/리비전/문서 기준/계약 버전 | 위 `context_snapshot`과 작업 실행 메타데이터 | 모델 요청·작업 조회·승인 stale 판정에서 동일 값 사용 |
| 미저장 문단과 편집기 증거 | 기존 `RewriteTask.snapshot`, `base_version` | 컨텍스트를 붙여도 현재 문단 fence는 약화하지 않음 |
| 실제 정규화 입력 해시 | 기존 `execution.input_sha256`; 입력 형식 버전도 함께 보관 | 목적·사실·기준을 포함해 **실제 전달하는 값**에서 산출 |
| 프롬프트 계약 버전 | 기존 `execution.prompt_contract` | 현재 계약과 구별되는 새 버전을 명시. 기존 작업을 소급 변경하지 않음 |
| 확인 기록 | 각 사실/기준의 `confirmed_by`, `confirmed_at`, `confirmation_id`, 원출처 유형·참조 | “사용자 확인”의 범위와 AI 원출처를 나중에도 구분 가능 |

메타데이터 JSON을 재사용하면 초기 단계에 새 테이블 없이 표현 가능하다. 다만 이는 저장 공간이 있다는 판단일 뿐, 기능이 구현됐다는 뜻은 아니다. 입력 스키마, 서버 검증, UI 확인 과정, 직렬화 계약, 작업용 MCP의 고정 입력 반환, LLM 입력 구성, 크기 제한, 공개 메타데이터 필터가 후속 구현 대상이다. 실제 값은 권한 있는 작업 입력 경로로 조회하고, 목록 화면에는 리비전·출처 요약·해시만 표시하는 방안을 권장한다. 토큰·인증 파일·연결 인증값은 넣지 않는다.

정규화 규칙도 계약 일부로 고정한다. 예를 들어 `rewrite-context-v1`의 필드 화이트리스트, UTF-8, 키 정렬, 고정 JSON 구분자, 사실 항목의 명시적 순서, 줄바꿈 정규화를 정한다. 의미가 바뀌는 임의 공백 제거·사실 합치기·Unicode 정규화는 하지 않는다. 이 규칙으로 만든 동일 바이트를 해시하고 실제 모델 입력의 데이터 부분으로 사용한다. 기존 `input_sha256`의 직렬화 방식을 새 규칙으로 과거 데이터에 소급 적용하지 않는다. provider별 시스템 지시문은 `prompt_contract`와 소스 manifest로 식별한다.

## 접수·생성·승인 순서

1. 현재 사용자 권한, 해당 대화가 가리키는 문서, 임대 소유자·토큰·만료를 검사하고 문서 행을 잠근다. 기존 동작과 같은 잠금 순서를 유지한다.
2. 클라이언트의 기대 `context_id/revision` 및 문서 기준 버전과 현재 값을 비교한다. 불일치·오래된 문서 기준·미해결 사실 충돌은 명시적 충돌로 반환한다. 이전 목적/사실을 자동으로 새 문서에 유효하다고 표시하지 않는다.
3. 실제 목적·확인 사실·작성 기준·출처·확인 기록·현재 문단 스냅샷·계약 버전과 정규화 입력 해시를 하나의 불변 작업 입력으로 만든다. 작업과 함께 commit한 뒤에만 실행한다.
4. worker는 접수 때 만든 불변 입력만 읽는다. 최신 컨텍스트나 전체 대화를 다시 읽어 값을 추가하거나 교체하지 않는다. 현재 문서 권한/임대/작업 상태의 재검사는 입력 고정과 별도로 유지한다.
5. 생성 후 승인 전에 문서 기준이나 컨텍스트 리비전이 바뀌면 기존 후보를 `stale`로 표시한다. 후보와 승인 이력은 보존하고, 새 스냅샷·새 작업 ID로 다시 검토한다. 새 내용으로 기존 후보·승인 ID를 바꾸어 강제 적용하지 않는다.
6. 이미 commit된 저장의 같은 출력·키 재확인은 신규 적용과 구분한다. 현재 접근 권한은 다시 검사하되, 이후 컨텍스트 변경을 이유로 완료된 저장을 취소·롤백하거나 새 모델 호출을 만들지 않는다. UI는 저장 확인 실패와 실제 rollback을 혼동하지 않는다.

동일 작업 ID의 재확인은 먼저 현재 접근 권한을 검사한 뒤 기존 불변 요청과 비교한다. 같은 ID에 다른 context revision/실제 값/문서 기준을 전달하면 기존 충돌 계약을 따른다. 기존 작업이 참조한 최신 컨텍스트 행을 덮어 읽거나 재실행하지 않는다. 현재 리비전 충돌 정책은 새 작업 접수와 아직 적용하지 않은 후보에 적용하며, 이미 확정된 저장의 멱등 확인에는 다른 분기를 둔다.

## 오래된 정보와 복원

문서 버전이 바뀌면 목적·사실의 재사용 여부를 사용자가 다시 확인하도록 표시한다. 데이터 손실 없이 새 리비전을 만드는 방식으로 확인을 기록한다. 사실 A와 사실 B 또는 출처의 내용이 충돌하면 항목을 함께 표시하고 명시적 선택·수정을 받은 뒤 새 리비전을 만든다. 작성 기준이 원문의 이름·날짜·금액·부정 의미와 충돌하면 자동 축약이나 의미 변경으로 해결하지 않는다.

새 세션은 DB의 컨텍스트와 권한 있는 작업의 불변 입력을 읽어 화면과 재현용 입력을 구성한다. 일반 대화는 일반 대화로, AI 과거 답변은 AI 출력으로, 확인 사실은 확인 기록이 있는 항목으로 구분해 표시한다. 이전 모델·MCP·파일 도구 호출은 복원 과정에서 재실행하지 않는다. 승인·영수증·확정 버전의 저장 증거가 없으면 복원만으로 “적용/저장 완료”라고 표시하지 않는다.

## 별도의 인수 기준

| 단계 | 완료를 입증할 시험 | 현재 상태 |
|---|---|---|
| DB 보관 | CAS 충돌, 문서 접근 제어, 확인 주체 위조 거부, 최신 컨텍스트 변경 뒤 과거 작업 입력 보존, 재시작 후 동일 값·출처 조회 | 기존 목적/사실 저장 기능은 존재. 이번 확장 계약은 설계만 |
| 새 세션 입력 재구성 | 이전 세션과 동일한 데이터 바이트·해시·계약 버전 재구성, AI/사용자 확인 구분, 오래된 기준 표시, 도구 재실행 0회 | 미구현·미검증 |
| 실제 모델 후속 생성 | 명시적으로 승인된 실제 Codex 실행에 정확한 고정 입력 전달, 후보 두 개와 provenance 연결, 리비전 변경 후 새 작업만 새 값 사용 | 이번 작업의 실제 모델 호출 0회. 후속 별도 승인 범위 |
| 사람 승인 후 저장 | 사용자의 실제 후보 클릭 증거, exact command/영수증/바이트/DB commit 연결, 후속 미저장 편집 분리 | 위 설계의 실제 사람 시험은 미실행. 자동 클릭은 대체 증거가 아님 |

각 단계의 완료 상태를 따로 보고한다. DB에 문자열이 저장됐다는 사실만으로 모델이 사용했다고 하거나 `context_used=true`로 바꾸지 않는다.
