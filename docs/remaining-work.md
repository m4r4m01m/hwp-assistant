# 남은 작업과 차단 요인

2026-09-27 갱신. 계획 v0.4 요구사항은 삭제하거나 완료로 고치지 않았다. 새 일정·공수는 산정하지 않았다. 문서 권한·대화·컨텍스트·변경분 저장·MCP·전체 문서 양식 적용은 [별도 구현 안내](collaboration-and-mcp.md)와 [검증 기록](verification-2026-09-27.md)을 참조한다.

## 우선순위

**현재 진행 기준:** 사용자 요청에 따라 Docker 작업은 보류한다. 아래 배포 검증 항목은 필요 조건으로 남기되, 지금 실행할 작업으로 해석하지 않는다. 현재 구현은 기존 Git 이력을 보존한 [PR #19](https://github.com/m4r4m01m/hwp-assistant/pull/19)로 관리한다.

1. **수정 엔진의 Docker 실빌드·배포 확인**: 없음 센티넬 패치를 Docker 코어→Studio→앱 빌드 경로에 연결했다. 기본 빌드는 패치 누락·해시 불일치·진단 코어를 거부한다. Windows wasm-pack의 no-opt 빌드, 실제 WASM 검사, 완성 앱의 15178 저장·재열기 시험은 통과했다. Docker/WSL Linux가 없어 Binaryen 최적화·컨테이너 실행은 미검증이며 기존 기본 서비스 엔진은 보존했다. 다음 최소 작업은 Docker Linux 환경에서 `docker compose build web`을 실행하고 배포 번들 검사를 통과시키는 것이다. 단순 2×2 표의 한컴 셀 편집·왕복·내용/서식/구조 보존도 통과했지만 125% 편집 화면에서 외곽선이 보이지 않는 차이는 미해결이다. 저장 XML과 한컴 자체 PNG에는 외곽선이 있다. 그림·필드·복합/반복 왕복은 미검증이다. [후속 결과](evidence/engine-release-and-table-2026-09-27.json), [빌드 경로](engine-empty-fill-fix.md).
2. **PostgreSQL/Compose**: 이 PC에 Docker·PostgreSQL 실행 파일이 없다. Compose 이미지 빌드, 행 잠금·경쟁 저장, 재시작·볼륨 복원, Linux fsync를 실제 환경에서 시험해야 한다. 현재 경쟁/영속성 테스트는 SQLite와 네이티브 프로세스다.
3. **실제 로컬 LLM**: `127.0.0.1:1234/v1/models` 연결 거부. 서버 기동, `/models`에서 ID 확인 후 실제 문단 품질·timeout·한국어 사실 보존 평가. Qwen 3.8의 실제 ID/규격은 아직 미확인.
4. **격리 실행**: 브라우저 핵심 시나리오에서 외부 HTTP 요청 0건은 확인했지만 인터넷 차단 환경의 AI 포함 전체 동작은 미검증이다. 사전 이미지·의존성·폰트 고지 반입, 외부 차단 후 확인.
5. **운영 보강**: 사용자별 토큰·문서 ACL과 추가형 스키마 002는 구현했다. SSO/운영 계정 관리, DB+파일 함께 백업, 참조 없는 실패 파일 정리, 격리 후보 관리 UI, 이후 SQL 번호 마이그레이션 확장, 배포 이미지 digest/SBOM, 의존성/폰트 고지 감사는 남아 있다.

## 이번 버전 밖

폴더/정렬/이동 등 전체 드라이브 확장, 휴지통, 공개 링크 공유, 양식 기반 AI 초안, 코드 기반 규칙 검사, 양식 블록 삽입·변수 치환은 **미구현 후속 범위**다. 문서별 owner/editor/reader 권한, 문서 권한에 따른 대화 공유, HWPX 양식 등록·추천·새 문서 복사는 구현했다. 모든 문서 권한자가 작성자와 관계없이 대화·후보·적용 이력을 열람한다. 실시간 공동편집·동시 커서·자동 병합·SSO·전자결재·대규모 RAG·모델 학습·실제 사내 인프라 구축은 추가하지 않았다.

## 엔진 제약과 앱 미구현 구분

- 엔진: 안전 AI 적용 대상이 본문 단일 서식 문단으로 제한됨. 표 셀은 수동 편집할 수 있지만 AI 자동 적용 대상이 아님. HWPX 손실 보고와 폰트 대체의 한계가 있음.
- 앱: 복잡한 문서 의미 차이·레이아웃 비교는 미구현. 서버의 리소스 누락 검사는 일부 개체와 BinData 누락을 보수적으로 탐지하며 정당한 그림 삭제도 막을 수 있음. 격리 후보 파일은 저장 키를 오류에 남기고 관리자는 파일 볼륨에서 회수; 사용자는 편집기의 복구 다운로드를 사용.
- 앱: 저장 실패 재시도 상태는 열린 탭의 메모리에 보관. 브라우저 강제 종료 후 저장 요청 큐를 복원하는 전용 기능은 없음. 엔진 자체 복구 draft가 모든 실패를 복구한다고 보장하지 않음.
- 앱: AI 결과의 JSON 형식·원문·적용 범위는 검사하지만 사실성/회사 규정 적합성은 판정하지 않음.
- 빌드: rhwp 고정 업스트림의 npm audit 개발 의존성 5건(low 1, moderate 1, high 3). 배포 런타임 `--omit=dev`는 0건. 업스트림 lock을 임의 변경하지 않았고 빌드 도구 업데이트 검토가 남음. 앱 프런트엔드는 audit 0건.

## 최초 시작 상태 — 과거 기록

최초 착수 당시 로컬은 `.git`만 있고 커밋·원격·미커밋 코드가 없었다. 일반 git 인증으로 대상 저장소를 읽을 수 없었으나 연결된 GitHub 도구로 계획 문서·PoC·로드맵을 확보해 원문 그대로 보존했다. 당시 원격 README/AGENTS는 404였고 산출물은 미커밋 상태였다.

2026-09-27 후속 작업에서 Windows Git 인증과 `origin` 연결을 완료하고 기존 `main` 이력 위의 `codex/initial-implementation` 브랜치에 구현을 커밋·푸시했다. DB·실문서·인증·PC별 설정·캐시는 제외했으며 기존 로컬 작업 파일을 보존했다. 위 최초 상태를 현재 Git 상태로 해석하지 않는다.
