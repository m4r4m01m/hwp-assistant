## 1. 개요

### 1.1 목적

HWP Assistant를 공모전 제출 및 시연을 위한 웹서비스로 배포한다.

기존에 보유한 Ubuntu Server PC를 활용하여 별도의 클라우드 서버 임대 비용을 최소화하고, 외부 사용자가 HTTPS를 통해 서비스에 접근할 수 있도록 구성한다.

LLM 추론은 시연 기간에 외부 API를 이용하되, 향후 사내 온프레미스 Qwen 모델을 활용할 수 있도록 제공자 교체가 가능한 구조를 지향한다.

### 1.2 운영 조건

## 2. 네트워크 및 서비스 진입점

### 2.1 현재 구축된 환경

다음 사항은 사용자 환경에서 구성된 것으로 확인하였다.

- Ubuntu Server PC에 Tailscale 설치 및 Funnel 구성
- Nginx 리버스 프록시 구성
- 서비스 경로 `/hwp-assistant/` 설정
- 내부 23000번 포트를 대상으로 요청 전달
- 외부 접속 URL 확보

**외부 서비스 URL**

`https://pseudowasabi-svr.taile7b6c4.ts.net/hwp-assistant/`

**내부 애플리케이션 진입점**

`127.0.0.1:23000` (배포 시 사용할 바인딩 기준)

23000번 포트를 HWP Assistant의 단일 진입점으로 사용한다.

기존 ipTIME DDNS와 포트포워딩 방식의 연결 테스트는 성공했으나, 실제 애플리케이션 공개는 현재 구성한 Tailscale Funnel을 활용한다.

### 2.2 요청 흐름

```text
[외부 사용자]
       |
       | HTTPS
       v
[Tailscale Funnel]
       |
       v
[기존 Ubuntu Nginx]
       |
       | /hwp-assistant/* → /* (접두 경로 제거)
       v
[127.0.0.1:23000]
       |
       v
[HWP Assistant Web Container]
  - Nginx
  - React 정적 파일
  - rhwp / WASM / 글꼴
       |
       | /api/*
       v
[FastAPI Container :8000]
       |
       +---- [PostgreSQL :5432]
       |
       +---- [HWPX 영속 파일 저장소]
       |
       +---- [LLM Provider]
                    |
                    v
             [외부 LLM API]
```

외부 사용자는 Tailscale Funnel을 통한 HTTPS 주소로 접근한다.

기존 Ubuntu Nginx는 `/hwp-assistant/` 접두 경로를 `/`로 치환한 후 내부 애플리케이션의 23000번 포트로 전달한다. 이는 실제 공유된 설정의 `proxy_pass http://127.0.0.1:23000/;` 끝에 `/`가 있기 때문이다.

애플리케이션 내부에서는 웹 컨테이너가 정적 리소스를 제공하고, API 요청을 FastAPI로 전달한다.

PostgreSQL 및 FastAPI의 내부 포트는 외부로 직접 공개하지 않는다.

### 2.3 URL 경로 처리 원칙

HWP Assistant는 도메인 루트(`/`)가 아니라 `/hwp-assistant/` 하위 경로에서 서비스된다.

따라서 다음 사항을 반영해야 한다.

1. 프런트엔드의 기본 경로를 `/hwp-assistant/`로 설정한다.
2. JavaScript, CSS, WASM, 글꼴 등의 리소스 경로를 하위 경로 기준으로 제공한다.
3. 브라우저의 API 요청은 `/hwp-assistant/api/`를 사용하도록 구성한다.
4. 내부 프록시는 해당 요청을 FastAPI의 기존 `/api/` 경로로 전달한다.
5. SPA 새로고침 및 직접 URL 접근 시에도 정상적으로 페이지를 반환한다.
6. 로그인·문서 다운로드·리다이렉트·문서 편집기 워커 등의 경로를 검증한다.

**프록시 경로 처리 기준 — 실제 호스트 설정 확인 (2026-10-22)**

Ubuntu 서버의 `/etc/nginx/sites-available/side`에 구성된 관련 설정은 다음과 같다.

```nginx
location /hwp-assistant/ {
    proxy_pass http://127.0.0.1:23000/;
    include /etc/nginx/proxy_params;
    proxy_set_header X-Forwarded-Proto https;
}
```

Nginx의 `proxy_pass`에 **후행 슬래시(`/`)가 포함**되어 있으므로, 이 `location`에 일치한 `/hwp-assistant/` 접두사를 `/`로 치환한다. 즉, **브라우저에서는 하위 경로를 사용하지만 23000번 포트의 애플리케이션 웹 컨테이너는 루트 경로를 받는다.** 이 호스트 설정을 유지하며 앱의 외부 리소스 URL을 조정한다.

| 브라우저에서 요청하는 외부 경로 | 호스트 Nginx가 23000번으로 전달하는 경로 | 내부 역할 |
|---|---|---|
| `/hwp-assistant/` | `/` | React HTML |
| `/hwp-assistant/assets/*` | `/assets/*` | JS·CSS 정적 파일 |
| `/hwp-assistant/rhwp/*` | `/rhwp/*` | 편집기 엔진·WASM·글꼴 |
| `/hwp-assistant/api/*` | `/api/*` | 내부 웹 Nginx → FastAPI `/api/*` |
| `/hwp-assistant/compare-renderer.html` | `/compare-renderer.html` | 비교 화면 |

**코드 연동 시 확인할 사항**

- 현재 `frontend/vite.config.ts`는 외부 하위 경로용 `base`를 지정하지 않는다. 배포용 빌드는 `/hwp-assistant/` 기반의 JS/CSS/HTML 공개 URL을 생성하도록 수정한다.
- 현재 `frontend/src/api.ts`의 `fetch("/api" + path)`와 파일 다운로드 URL은 절대 경로이다. 외부 `/hwp-assistant/api/*`로 요청하도록 조정하되, **내부 FastAPI 라우트는 기존 `/api/*`로 유지**한다.
- 프런트엔드에서 직접 구성하는 `/rhwp/*`, WASM, 워커, 비교 화면, 폰트 경로도 확인한다. Vite의 `base` 변경만으로 모든 런타임 절대 경로가 자동 수정되지는 않는다.
- 현재 `frontend/nginx.conf`는 API 프록시에서 `X-Forwarded-Proto $scheme`을 사용한다. Tailscale Funnel과 호스트 Nginx에서 외부 HTTPS를 처리하지만, 내부 웹 컨테이너의 `$scheme`은 HTTP일 수 있다. **원래 외부 HTTPS 정보를 보존해 FastAPI에 전달하는 방법**을 배포 시 검증한다.
- 루트 `/api/*` 또는 `/assets/*`로 브라우저 요청이 새어나가지 않는지, SPA 직접 접근·로그인·저장·다운로드·Web Worker를 실제 외부 주소에서 확인한다.

기존 호스트 Nginx의 다른 서비스 경로(`/banking-message-assistant/`, `/ubuntu-connection-test/`)는 이번 HWP Assistant 배포 변경 대상이 아니다.

## 3. 애플리케이션 배포 구조

### 3.1 Docker Compose 기반 운영

기존 저장소의 `compose.yaml`을 기반으로 다음 세 서비스를 배포한다.

| 서비스 | 역할 | 외부 공개 |
|---|---|---|
| `web` | Nginx, React, rhwp 정적 리소스 제공 및 API 프록시 | 호스트 loopback의 23000번 포트 |
| `api` | FastAPI, 문서 관리, AI 작업, 버전 관리 | 비공개 |
| `db` | PostgreSQL, 문서 메타데이터 및 작업 상태 보관 | 비공개 |

초기 배포는 단일 Ubuntu 서버에서 실행하며 별도의 Kubernetes, 로드밸런서, 관리형 데이터베이스를 도입하지 않는다.

### 3.2 포트 구성

| 구성 요소 | 포트 |
|---|---|
| 애플리케이션 진입점 | 호스트 `127.0.0.1:23000` |
| Web 컨테이너 | `80` |
| FastAPI 컨테이너 | `8000` |
| PostgreSQL 컨테이너 | `5432` |

Docker Compose에서 웹 컨테이너의 포트 매핑을 다음과 같이 변경하는 방안을 채택한다.

```yaml
ports:
  - "127.0.0.1:23000:80"
```

기존 `8080` 바인딩을 `23000`으로 변경하며 다른 포트는 Docker 내부 네트워크에서만 사용한다.

### 3.3 프런트엔드 배포

- React와 TypeScript를 프로덕션 빌드한다.
- 수정된 rhwp 편집기 엔진 및 WASM을 포함한다.
- Nginx에서 정적 파일을 제공한다.
- 개발용 Vite 서버는 운영 환경에서 실행하지 않는다.
- 기존 편집기 엔진의 버전 고정, 패치 및 무결성 검사를 유지한다.

현재 최적화된 Docker/WASM 배포 빌드의 실제 실행 검증은 별도로 필요하다.

### 3.4 백엔드 및 데이터 저장

FastAPI는 단일 인스턴스로 시작한다.

기존 문서 저장, 편집 세션, 버전 관리, AI 수정 후보 검증 및 승인 흐름을 유지한다.

PostgreSQL과 HWPX 파일 저장소에는 영속 볼륨을 사용한다.

다음 데이터는 컨테이너 재시작 및 이미지 재배포 이후에도 보존해야 한다.

- 문서 메타데이터 및 사용자 권한
- HWPX 원본과 모든 확정 버전
- 문서별 대화와 작성 정보
- AI 수정 후보 및 적용 이력
- 보고서 생성 작업 기록

데이터베이스와 문서 파일은 서로 참조하므로 백업과 복원 시 일관성을 유지해야 한다.

## 4. LLM 연결 아키텍처

### 4.1 기본 방향

LLM은 애플리케이션 내부에서 직접 실행하지 않는다.

시연 환경에서는 FastAPI가 외부 LLM API를 호출하고, 향후 사내 환경에서는 내부 Qwen 추론 서버를 호출하도록 설계한다.

```text
[HWP Assistant FastAPI]
          |
          v
  [LLM Provider 인터페이스]
          |
          +-- 외부 API 제공자
          |      (공모전 시연)
          |
          +-- 사내 Qwen 제공자
                 (사내 적용 목표)
```

모델이 문서 전체를 직접 변경하거나 저장하지 않는다.

모델의 생성 결과는 기존 애플리케이션에서 검증하고, 사용자의 승인 이후 HWPX 편집 및 버전 저장 흐름으로 전달한다.

### 4.2 현재 구현과 추가 개발 범위

현재 `main`에는 OpenAI 호환 HTTP API 기반 `LlmProvider`가 구현되어 있다.

문서 대화, 문장 검토, 문단 수정 후보 생성에 활용할 수 있으나 외부 유료 OpenAI API 주소는 현재 구현에서 차단하고 있다.

또한 새 보고서 생성과 보완 요청은 Codex app-server 기반 실행기에 의존한다.

따라서 다음 추가 작업이 필요하다.

1. 외부 LLM API 사용을 명시적으로 허용하는 시연 환경 구성
2. 공급자별 API 요청 파라미터와 응답 형식 호환성 처리
3. 보고서 생성 및 보완 기능의 LLM 제공자 추상화
4. 기존 보고서 결과 계약 및 검증 규칙 재사용
5. 외부 API 호출에 대한 비용·동시 실행·요청 횟수 제한
6. 생성 작업의 실패, 중단 및 재시도 처리 유지

기존 Codex/MCP 경로는 개발 및 비교 검증 용도로 보존할 수 있다.

### 4.3 웹 검색 기능

현재 보고서 생성의 웹 검색은 Codex 실행기와 연결되어 있다.

일반 외부 LLM API 호출만으로 기존 웹 검색 기능이 자동 제공되는 것은 아니다.

초기 시연에서는 사용자 제공 자료를 기반으로 보고서를 생성하는 방식을 우선 검토한다.

공개 자료 검색을 필수 시연 범위에 포함할 경우, 외부 검색 도구 또는 검색 API를 별도로 연계하고 출처 검증을 수행한다.

### 4.4 사내 Qwen 모델 연계

사내 온프레미스 모델을 이용하는 것은 향후 적용 시나리오로 제시한다.

모델 서버의 정확한 ID, API 호환성, 문맥 길이, 구조화 출력 성능과 한국어 보고서 품질은 별도로 검증한다.

공모전 외부 시연에서 사내 모델을 실제 사용한 것처럼 표현하지 않는다.

외부 LLM API와 내부 모델을 자동으로 교차 호출하지 않으며, 운영 환경에 따라 명시적으로 선택한다.

## 5. 보안 구성

### 5.1 외부 접근

- 외부 사용자 접속에 HTTPS 사용
- Tailscale Funnel을 통해 서비스 공개
- ipTIME에서 애플리케이션용 직접 포트포워딩 불필요
- 내부 API 및 PostgreSQL 포트는 외부에 공개하지 않음
- 불필요한 기존 포트포워딩과 UFW 규칙 정리

Tailscale Funnel은 공개 접속 경로이므로 애플리케이션 자체 인증이 필요하다.

### 5.2 사용자 인증 및 접근 권한

기존 HWP Assistant의 사용자별 토큰 인증과 문서 권한 체계를 이용한다.

운영 환경에서는 무인증 `local` 단일 사용자 모드를 사용하지 않는다.

시연 사용자별 계정 및 접근 가능한 문서를 명시적으로 구성한다.

### 5.3 API 키 및 문서 보호

- API 키와 DB 비밀번호를 Git 저장소에 커밋하지 않는다.
- 환경변수 또는 서버의 비밀정보 파일로 관리한다.
- 실제 사내 문서를 외부 LLM API로 전송하지 않는다.
- 공모전 시연에는 공개 자료 또는 합성 문서를 사용한다.
- 모델 호출량 및 요청 크기에 상한을 적용한다.
- 필요시 평가자용 계정의 이용 기간을 제한한다.

## 6. 배포 및 운영 절차

### 6.1 초기 배포

1. Ubuntu에 Docker Engine 및 Compose 구성
2. GitHub `main` 기준 배포용 작업 브랜치 준비

## 11. 23000 포트 배포 기반 구현

- 개발용 `compose.yaml`은 보존하고 **`compose.deploy.yaml`을 단독 사용**한다. 호스트 포트는 `127.0.0.1:23000:80`이다.
- web, API, PostgreSQL은 같은 Compose 프로젝트의 별도 컨테이너다. PostgreSQL 데이터와 HWPX 파일은 두 개의 외부 영속 볼륨에 보관한다.
- Vite·독립 Studio 빌드·API·다운로드·비교 렌더러·글꼴의 공개 URL에 `/hwp-assistant/`를 반영한다.
- 운영 전용 컨테이너 Nginx는 로그인/로그아웃 쿠키 Path를 변환하고 HTTPS 전달 정보를 보존한다. API는 전용 비공개 네트워크에서만 프록시 헤더를 신뢰한다.
- 호스트 Nginx의 경로 분기는 유지하되, 본문 한도와 중복 전달 헤더를 점검한다. 적용 예시는 `deploy/host-nginx-location.conf.example`이며 다른 서비스는 수정하지 않는다.
- 운영 토큰·DB 비밀번호가 없거나 형식이 잘못되면 시작을 거부한다. 초기화·백업·로컬 빌드/pull 배포·상태 검증 스크립트를 제공한다.
- GitHub Actions는 PR/main의 가벼운 검사와 명시적으로 요청하는 이미지 빌드/실행 검증/GHCR 게시를 분리한다. 집 서버 배포는 별도 runner 설정과 수동 실행 선택이 있어야 동작한다.
- **이번 구현은 외부 LLM 또는 보고서 생성기 전환 완료를 뜻하지 않는다.** 해당 내용은 4절의 후속 개발 범위로 남긴다.
- 작성 환경에서의 단위·문법 검사, 실제 컨테이너 CI, 실제 집 서버·브라우저·한컴 검수를 서로 구분한다. 확인되지 않은 실행을 완료로 표시하지 않는다.
