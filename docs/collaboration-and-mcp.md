# 문서 권한·대화·컨텍스트·변경분·템플릿

2026-09-27 구현 안내. 기존 앱을 확장했으며 `internal-doc-assistant-plan-v0.4.md`는 요구사항 원문으로 보존했다. 별도 첨부 실행 지시문은 작업 폴더와 메시지에서 확인되지 않아, 이번 사용자 메시지에 명시된 다섯 가지 핵심 범위를 기준으로 구현했다. 새 일정·공수는 산정하지 않았다.

## 권한과 인증

`HWP_AUTH_TOKENS`는 `{"사용자ID":"무작위 토큰"}` 형식의 서버 환경변수다. 각 토큰은 서로 달라야 하고 24자 이상이어야 한다. 사용자 ID를 요청 헤더로 보내는 방식으로 인증하지 않는다. 브라우저는 로그인 후 HttpOnly / SameSite=strict 쿠키를 사용하며 HTTPS 접속에서는 Secure도 설정한다. API/MCP는 `Authorization: Bearer ...`를 사용한다. 토큰·사용자 변경은 서버 재시작으로 반영한다. 원격 배포는 HTTPS와 별도의 운영 접근 통제가 필요하다. SSO·사용자 등록·토큰 발급 UI는 구현하지 않았다.

토큰 생성 예:

```powershell
.venv/Scripts/python -c "import secrets; print(secrets.token_urlsafe(32))"
```

실제 토큰은 환경변수/비밀 설정에만 둔다. `.env`는 Compose가 읽고 네이티브 서버는 자동으로 읽지 않는다. 인증을 설정하지 않으면 기존 동작을 이어가는 `local` 단일 사용자 개발 모드다. 이 모드는 서로 다른 사람을 구분하거나 보호하는 모드가 아니다.

| 권한 | 조회 | 대화·컨텍스트 작성 | 문서 편집·저장 | 공유 권한 변경 |
|---|---|---|---|---|
| reader | 문서·버전·모든 작성자의 대화·미적용 후보·적용 이력·접근 가능한 템플릿 | 불가 | 불가 | 불가 |
| editor | 가능 | 가능 | 가능, 본인 편집 임대 필요 | 불가 |
| owner | 가능 | 가능 | 가능, 본인 편집 임대 필요 | 가능 |

업로드한 사용자가 소유자다. 문서 목록의 **공유 권한**에서 등록된 사용자에게 열람/편집 권한을 부여한다. 최신 정책에 따라 문서 권한자는 작성자와 관계없이 모든 대화·미적용 후보·적용 이력을 읽는다. 개인에게 문서 접근권을 부여하는 공유 기능은 유지하지만, 공유 문서 안에서 작성자만 읽는 비공개 대화는 제공하지 않는다. 기존 `private` 행과 작성자 기록은 삭제하거나 변경하지 않고 문서 ACL로 열람을 판단한다. 모든 대화·메시지·컨텍스트·제안 API가 현재 문서 권한을 다시 검사한다. 권한을 회수하면 개인 대화도 접근할 수 없다. 이미 다운로드했거나 브라우저에서 읽었던 내용을 회수하는 기능은 아니다.

권한 변경은 문서 행을 잠그고 열린 편집 임대를 무효화한다. 권한 변경 뒤에는 편집기를 다시 열어야 한다. 편집 임대는 발급받은 사용자에게 귀속되므로 다른 사용자가 임대 토큰만 알아도 저장할 수 없다. 열람 화면은 저장본 다운로드와 대화를 제공하며 편집기를 열지 않는다.

## 기존 데이터 이관

`python -m app.migrate`와 앱 시작은 추가형 스키마 002/003을 적용한다. 기존 documents/versions의 열과 원본·과거 HWPX 파일은 변경하지 않는다. DDL은 `backend/migrations/002_collaboration.sql`, 데이터 권한 이관은 `backend/app/schema.py`에 있다.

기존 공용/단일 사용자 문서가 있는 상태에서 인증을 켜려면 **`HWP_LEGACY_OWNER`에 등록된 사용자 ID를 명시**해야 한다. 임의 사용자에게 기존 문서를 할당하지 않는다. 명시한 소유자에게 기존 local 문서 권한과 개인 대화 소유권을 이관한다. 작성 당시 메시지 작성자 표시와 불변 파일은 유지한다. 이관 전 DB와 파일 볼륨을 함께 백업한다. SQLite 이관 시험은 통과했고 PostgreSQL 실기동 이관은 미검증이다.

## 자체 컨텍스트와 대화

현재 편집기에서는 **문서 AI 대화 → 대화 이름 입력 → AI와 대화 시작**을 선택한다. 모든 문서 권한자가 열람한다. 구형 클라이언트의 `private` 생성 요청은 `document`로 정규화하며 기존 `private` 기록도 문서 권한자에게 보인다. 공개를 위해 reader의 쓰기 권한을 넓히지 않는다.

2026-10-23 추가한 문서 대화는 요청 당시의 미저장 본문·표 텍스트와 최근 완료 대화 10턴을 사용한다. **AI가 읽을 내용 확인**에서 포함 범위를 볼 수 있고, 그림·화면 배치는 읽지 않는다. 선택 본문 문단의 수정 요청은 **이 문단 수정 후보 만들기**를 통해 기존 후보 비교·승인·저장으로 이어진다. 질문 자체는 문서를 변경하지 않는다. 현재 설정과 제한은 [README의 AI 사용 안내](../README.md#ai-설정)를 참조한다. 아래의 저장한 컨텍스트·자유 메모 기능은 **작성 정보·검토 메모** 안에 있다.

작성 목적·확정 사실·작성 기준은 **컨텍스트 저장**으로 DB에 보관한다. **현재 문단을 Codex에 공유**는 그 내용과 rhwp의 문단 위치·문서 상태·원문/서식/인접 문맥 해시를 함께 저장한다. 컨텍스트는 대화별 리비전과 문서 기준 버전을 갖는다. 다른 사용자의 컨텍스트 수정을 덮어쓰거나 오래된 문서 기준으로 저장하려 하면 409로 거부한다. 이전 컨텍스트는 문서 저장 후 오래된 것으로 표시되므로 내용을 확인하고 다시 공유해야 한다.

**메시지 저장**은 모델 없이 동작한다. **설정된 AI에 질문**은 앱이 보관한 컨텍스트와 최근 20개 메시지를 기존 로컬/사내 LlmProvider에 전달한다. 모델 응답 전후로 권한과 문서/컨텍스트 기준을 검사한다. 실패해도 질문은 남는다. 대화 조회는 기본 최근 100개, API `limit`은 최대 200개다. 오래된 메시지도 DB에 남지만 전체 메시지 페이지 탐색 UI는 없다.

Codex나 모델의 응답으로 HWPX를 재생성하지 않는다. Codex 문단 제안은 별도로 저장하고 웹 편집기에서 **이 제안 승인하고 적용**을 눌러야 한다. 서버의 권한/임대/기준 검사 후 클라이언트가 rhwp exact command로 문서·선택·원문·서식·인접 문맥을 확인한다. 승인은 편집 버퍼 변경이며 서버 저장은 별도다.

## 변경분 저장

최초 업로드는 원본 HWPX 전체를 불변 파일로 저장한다. 기존 문서의 웹 저장은 기준 바이트와 결과 바이트의 공통 앞/뒤 부분을 제외한 **단일 바이너리 변경 구간**을 전송한다. 의미 기반 자동 병합이나 XML 재생성 방식이 아니다. 압축 문서에서는 변경 구간이 전체 파일에 가까울 수 있으며 용량 절감률은 보장하지 않는다.

요청에는 기준 버전, 편집 임대, 멱등 키와 함께 기준 파일 SHA-256, 제거 구간 SHA-256, 결과 SHA-256이 들어간다. 서버는 문서 행 잠금 안에서 사용자의 권한과 임대 소유자를 검사하고 변경분을 재구성한다. 기존 게시 경로가 임대·기준 버전·HWPX 형식·리소스 손실을 검사하고 새 파일 fsync 후 버전·변경분 메타데이터를 한 DB 트랜잭션으로 확정한다. 그 후에만 저장 완료를 응답한다.

버전 기록의 **변경분 보기**는 HWPX ZIP 내부 항목별 추가/삭제/변경을 보여준다. 글자 의미·쪽 배치·한컴 호환 판정은 아니다. 재업로드/복원도 기존 기준 버전·임대 검사를 유지하며 새로운 버전과 변경분 기록을 만든다. 통신 실패 시 동일 요청으로 재시도하고 저장 중 추가 입력은 미저장 상태를 유지한다. 열린 탭의 재시도 정보는 메모리에 있으며 탭 강제 종료 후 요청 큐 복원은 여전히 미구현이다.

## 템플릿

문서 목록의 **양식 등록**은 문서의 현재 불변 HWPX 버전을 고정한다. 이름·설명·태그는 메타데이터이고 원본 바이트는 수정하지 않는다. 목록의 **템플릿 추천 · 적용**에서 검색하면 접근 가능한 원본 문서에 연결된 양식만 이름/설명/태그 일치로 추천한다. 모델을 호출하지 않는 결정적 추천이며 추천 이유를 표시한다.

**이 양식으로 새 문서**는 양식 HWPX 바이트를 새 불변 파일·새 문서 ID로 저장하고 실제 rhwp 편집기로 연다. 표·서식이 있는 합성 HWPX로 적용→편집→변경분 저장을 시험했다. 원본 문서가 이후 수정돼도 등록한 버전은 유지된다. 원본 문서 권한이 회수되면 추천·새 적용이 차단되지만 이미 만든 별도 문서는 새 소유자의 문서로 남는다.

이번 구현의 적용 단위는 **전체 문서 양식으로 새 문서 생성**이다. 기존 문서에 표/제목 블록을 삽입하거나 변수 치환을 수행하는 템플릿 편집 기능은 구현하지 않았다. 미리 채워진 내장 양식은 없으며 보유한 합성/업무 양식을 등록해 사용한다.

## Codex / MCP

[공식 Codex MCP 설정](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)의 프로젝트별 stdio 구성을 사용한다. [공식 Python MCP SDK](https://github.com/modelcontextprotocol/python-sdk) 1.26.0과 하위 의존성을 별도 lock으로 고정했다. 웹/API의 필수 의존성에 MCP를 추가하지 않았다.

```powershell
.venv/Scripts/python -m pip install -r backend/requirements-mcp.lock.txt
codex mcp get hwp_assistant --json
```

프로젝트의 `.codex/config.toml`에 현재 Windows 경로를 등록했다. 다른 PC에서는 `command`, `cwd`, `PYTHONPATH`를 해당 체크아웃 경로로 바꾼다. API를 먼저 실행하고 Codex에 전달할 환경을 설정한다.

```powershell
$env:HWP_API_URL='http://127.0.0.1:8000'
$env:HWP_API_TOKEN='<본인의 앱 토큰>'
# 이 환경을 상속받는 Codex 프로세스에서 프로젝트를 연다.
```

개발 단일 사용자 모드에서는 HWP_API_TOKEN을 생략할 수 있다. GUI에서 이미 실행 중인 Codex는 다른 터미널에서 설정한 환경변수를 자동으로 상속받지 않는다. 설정 변경 후 MCP 연결/앱을 새로 시작해야 할 수 있다. 현재 채팅의 도구 목록에 서버가 실시간 추가됐다고 주장하지 않는다. API 토큰은 사용자별 문서 권한에만 쓰이며 OpenAI API 키가 아니다. 별도의 유료 API 호출이나 AI 자동 대체는 추가하지 않았다.

도구: `list_documents`, `list_conversations`, `read_context`, `append_reply`, `propose_text`, `recommend_templates`. 모든 호출은 동일한 HTTP API 권한 검사를 통과한다. 임의 경로·SQL·셸·권한 변경·HWPX 직접 저장 도구는 없다. stdio 서버는 외부 포트를 열지 않는다. 비 loopback API로 연결할 때는 HTTPS를 요구한다.

사용 예: 웹에서 문단 공유 후 표시된 대화 ID를 Codex에 전달하고 “이 대화의 컨텍스트를 읽고 문단 수정안을 제안해줘”라고 요청한다. 결과는 웹에서 대화 새로고침으로 확인하고 승인한다. SDK 클라이언트↔실제 stdio 프로세스↔인증 API 연결, 도구 호출, 문서 권한자의 다른 작성자 대화 열람, 권한 회수 후 재호출 차단을 시험했다. Codex CLI의 설정 인식도 확인했다. 기존 시험은 모델 없는 MCP 전송 시험이었다. 실제 모델 호출의 새 근거와 미실행 단계는 `verification-2026-09-27.md`의 추가 검증 기록을 참조한다.


## 실제 Codex 선택 문단 실행 경로 (2026-09-27 추가)

네이티브 서버와 같은 OS 사용자의 기존 ChatGPT 로그인을 사용한다. 설치된 CLI의 `codex login status`가 ChatGPT 로그인임을 확인하고, `codex exec --ignore-user-config --ephemeral --sandbox read-only --json`을 실행한다. 기존 설정에서는 모델 이름만 읽고 인증 파일을 복사하거나 앱 사용자에게 전달하지 않는다. CLI가 없거나 로그인·사용량·MCP 연결이 실패하면 해당 작업을 실패로 남기며 API 키나 유료 대체 경로로 전환하지 않는다. MCP 선택 의존성 `backend/requirements-mcp.lock.txt` 설치가 필요하다. Docker 안에 호스트 Codex 인증을 복사하는 구성은 제공하지 않는다.

`HWP_CODEX_USER`는 본인 Codex 환경과 연결되는 앱 사용자 ID다(기본 `local`). 인증을 켠 별도 시험 서버에서는 합성 계정 `alice`로 명시했다. 다른 앱 사용자에게 서버 소유자의 Codex 실행 권한을 자동 부여하지 않는다. `HWP_CODEX_API_URL`은 해당 서버의 loopback API 주소다. 다른 사용자의 실제 Codex 환경에서 후속 요청하는 흐름은 다음 검증 범위다.

**실제 Codex로 후보 2개 요청**은 요청 순간의 rhwp 선택 스냅샷을 별도 작업으로 고정한다. 작업 ID·문서 ID·기준 버전·리비전·문단 대상·원문/서식/문맥 해시를 보관하며 후보만으로 HWPX 버전을 만들지 않는다. 비교 중에는 자동 저장을 보류한다. 수동 저장으로 기준이 바뀌면 기존 후보는 충돌 상태가 된다.

문서 실행기는 빈 임시 작업 디렉터리에서 shell/file editing/web/apps/plugins 등을 끄고 별도 MCP 서버의 `read_rewrite_task`, `submit_rewrite_candidates` 두 도구만 사용한다. 일회 실행 토큰은 DB에 해시로만 저장되며 해당 작업 입력 조회·후보 제출만 허용한다. 문서 저장·승인·권한 변경·다른 문서 조회에 사용할 수 없다. 완료되거나 600초가 지나면 무효다. 실제 도구 완료 이벤트와 모델 turn 완료, 후보 2개 보관을 함께 확인해야 작업을 ready로 표시한다.

**후보 N 승인·적용·저장**은 명시적 버튼 클릭 후 서버가 권한·임대·기준을 검사한다. 공통 `EditorAdapter.apply`가 설치된 rhwp exact command로 대상 원문과 편집 상태를 다시 검사한다. 동일 적용 ID를 명령 ID와 저장 멱등 키로 유지하며, 적용 직후 출력의 해시와 엔진 영수증을 기록한다. 서버는 출력 해시와 실제 HWPX 대상 문단이 승인 후보와 일치하는지 읽어서 확인하고, 기존 변경분 게시 트랜잭션 안에서 새 버전과 적용 이력을 함께 확정한다. XML을 재작성하지 않는다.

승인/저장 응답 유실 시 같은 후보로 재시도한다. 원문·기준 충돌 시 후보와 미저장 버퍼는 유지된다. 브라우저를 강제 종료하면 메모리의 출력/재시도 큐는 복원하지 못하므로 복구용 다운로드를 제공한다. 서버가 작업 도중 종료되면 running 작업의 자동 재개는 아직 지원하지 않는다. DB에 컨텍스트가 남는 사실을 Codex 세션 없는 독립 복원 성공으로 해석하지 않는다.

일반 MCP의 `read_context`도 현재 문서 ACL로 다른 작성자의 대화·기존 제안·새 후보 작업·적용 이력을 반환한다. 문서 실행기용 두 도구는 승인·저장 기능을 갖지 않는다.

## 로컬·사내 후보 생성 경로 (2026-10-06 추가)

`HWP_REWRITE_PROVIDER=llm`을 명시하면 기존 `LlmProvider.rewrite`가 고정된 미저장 문단과 개선 지시로 두 후보를 생성한다. 기본값은 `codex`다. 로컬 경로는 서버의 `LLM_*` 설정만 사용하며 Codex·MCP·본인 Codex 계정 매핑을 요구하지 않는다. 문서 editor/owner와 본인 임대·기준 버전 검사는 그대로 적용한다. 양쪽 경로의 후보 검증과 게시 조건을 공통화했으며 기존 작업·승인·저장 테이블을 사용한다.

두 후보 요청에는 위에서 설명한 작성 목적·확정 사실·대화 내역을 아직 전달하지 않는다. 사용하지 않은 컨텍스트를 사용했다고 표시하지 않는다. 과거 작업의 제공자·모델과 현재 설정을 따로 표시하며 실제 모델 응답 여부는 검증 기록과 구분한다.

재시작된 서버는 중단된 생성 작업을 자동 재실행하지 않는다. 완료되지 않은 작업은 600초 뒤 만료로 표시하며, 요청자 또는 owner가 결과 수신을 중단할 수 있다. 기존 원문과 후보를 삭제하지 않는다. 실제 HTTP/CLI 프로세스 중단과 결과 게시 취소는 구분한다. 자세한 [설정·계약·실패 복구](local-model-rewrite.md)와 [새 검증 기록](verification-2026-10-06.md)을 참조한다.
