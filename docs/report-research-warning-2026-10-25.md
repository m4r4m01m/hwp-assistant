## 1. 변경 이유와 사용자 결정

사용자는 운영 이미지 `49dda2c`에서도 `research=true` 요청이 완료 검색 0건으로 끝나는 것을 확인했다. 후속 인계의 실패 종류는 `research_unavailable`, 마지막 단계 `writing`, 약 115초, 연결 준비 **1,931ms**, 첫 글 **21,738ms**다. 허용된 protocol 오류 종류·HTTP 상태는 관측되지 않았다. 이는 사용자의 인증된 운영 세션 관측이며 클라우드가 직접 모델을 호출해 확인한 수치가 아니다. 설정 오류나 특정 upstream 원인을 이 정보만으로 확정하지 않는다.

기존 정책은 모델이 정상 종료해 보고서 JSON을 반환해도 완료 검색이 없으면 전체 작업을 실패 처리했다. 사용자는 새 요청부터 **정상 완료·검증된 보고서는 자료 조회 미완료 경고를 남겨 내용 검토할 수 있도록 하는 변경**을 명시적으로 요청했다. 새 UI 요청은 경고 허용을 기본으로 사용하고 공개자료 조회 선택은 계속 켜 둔다. 별도 허용 체크를 반복해서 요구하거나 검색 옵션을 자동 해제하지 않는다.

## 3. 요청·원본 보존

정책은 새 요청 입력의 `research_policy`에 고정한다. 값은 `require_completed` 또는 `allow_unverified`이며 새 UI는 후자를 명시해 보낸다. 필드가 없는 과거 요청은 기존 엄격 정책으로 해석하고 필드를 소급 주입하지 않는다. 과거 입력 hash·동일 ID 결과 재조회 계약을 보존한다. 기존 실패 작업·완성 draft·수동 편집 HWPX·과거 버전을 소급 변경하거나 자동 재생성하지 않는다.

보완은 원래 draft와 SHA를 고정한 별도 작업이며 원래 요청의 정책을 상속한다. 과거 엄격 정책의 보완 작업을 새 UI 기본값으로 조용히 바꾸지 않는다. 원래 출처 ID·제목·URL·날짜의 보존 계약과 owner/status fence를 유지한다.

현재 작업의 경고와 제한은 서버가 관측한 완료 검색 수와 검증 결과로 결정한다. 브라우저가 상태를 `verified`로 주장하거나 후보 URL을 제출하는 것만으로 검색 완료를 증명할 수 없다. 정상 turn 종료·완료 메시지·ReportDraft 검증·현재 owner/status 확인을 생략하지 않는다.

## 4. 경고·출처·HWPX 경계

완료 검색 0건이면 출처 목록에 URL이 있더라도 이번 요청에서 공개자료를 조회·검증한 출처로 표시하지 않는다. 완료 검색이 있어도 도구 실행 횟수만으로 개별 URL이나 사실의 검증을 증명할 수 없으므로 새 정책의 `source_verification`은 `unverified`다. 출처 후보와 본문의 사실 주장을 검토할 수 있도록 보존하면서 **미검증 후보**라는 상태를 명확히 드러낸다. 모델 기억에서 생성된 URL을 확인된 출처로 표시하거나, 경고를 피하려고 링크·인용·사실을 지우거나, 자료 조회 성공 이력을 만들어 내지 않는다.

서버는 최종 draft에만 `research_notice`를 넣는다. `version=research-notice-v1`, 고정된 정책·요청 여부·상태(`not_requested`/`completed`/`unverified`)·관측한 시작/완료/미완료 검색 수(`started_calls`/`completed_calls`/`incomplete_calls`)·출처 검증 상태·고정 경고 code/message를 담는다. 경고 종류는 `research_incomplete`, `sources_unverified`, `research_not_requested`, `inherited_research_unverified`다. 경고 허용 요청은 완료 검색 0건이거나 실제 시작이 관측됐지만 완료되지 않은 조회가 있으면 `unverified`다. 조회 1건이 완료됐다는 이유만으로 다른 미완료 조회를 숨기지 않는다. 기존 엄격 정책의 최소 완료 검색 1건 조건은 그대로 유지한다. 이 필드는 모델 출력 schema에서 제외하며 모델이 직접 검증 상태를 선언하지 못한다. `execution.research`에는 관측 metadata, `execution.warnings`에는 UI용 경고를 함께 남긴다.

경고는 내용 검토 화면·서식 미리보기/편집 화면·결과/출처에 이어지고, 보고서의 확인 사항에도 반영돼 HWPX에서 확인할 수 있어야 한다. 기존 최대 6개 `limitations`를 자르거나 대체하지 않고 그 뒤에 동결한 notice를 렌더링한다. 경고·제한을 반영한 최종 draft를 검증하고 그 SHA를 기준으로 검토·서식·확정 저장한다. 보완 작업도 기존 미검증 경고를 보존한다. 수동 편집 뒤 확정 저장하는 바이트를 서버가 경고 삽입 명목으로 다시 쓰지 않는다. 웹 화면에만 일시적으로 알린 뒤 파일에는 최신 정보가 검증된 것처럼 남기는 흐름을 허용하지 않는다.

내용 검토 후 사용자가 문서 만들기를 선택해야 서식을 준비한다. 서버 저장은 표시된 내용과 경고를 검토한 사용자의 **초안 확정·서버 저장** 선택이 필요하다. 경고 초안을 받을 수 있도록 한 정책 변경이나 과거 배포 승인을 자동 저장 승인으로 해석하지 않는다. 원본 문서와 과거 버전은 불변이며 저장 응답이 유실되면 동결한 같은 결과를 재확인한다.

## 5. 적용 범위와 검증 한계

검색 command·고정 CLI·모델·도구 차단·기한을 임의로 바꾸거나 실제 검색 복구를 주장하지 않는다. 사용자가 입력한 prompt를 숨겨 교체하지 않으며 추가 모델 호출·자동 재요청·유료 AI fallback·research 자동 해제는 도입하지 않는다. 문단 수정 경로·계정/AI ACL·운영 private env는 보존한다.

사용자는 같은 후속 작업에서 **기존 스레드 chat·AI review 두 기능도 홈서버 Codex로 연결할 수 있도록 개발**해 달라고 별도로 명시했다. 이는 보고서 경고 정책과 다른 변경이며 [Codex chat/review 연결](codex-chat-review-2026-10-25.md)에서 다룬다. 기존 HTTP 명시 선택을 유지하고 장애 시 자동 provider 전환을 하지 않는다. 개발 요청을 운영 환경변수 변경·새 배포 승인으로 해석하지 않는다.

검증은 합성 app-server 이벤트·API·UI 및 확보한 고정 rhwp의 보고서 검토/서식/저장 경계를 구분한다. 실제 모델 호출과 운영 적용은 수행한 경우에만 별도 근거를 남긴다. 현재 클라우드에는 운영 인증정보가 없으며 실제 모델 호출은 0회다. 후속 변경의 main 병합·이미지 게시·새 운영 배포는 검토 가능한 코드·검증·위험이 준비된 뒤 별도 승인 범위로 판단한다.

## 6. 롤백과 신규 초안 호환성

DB schema migration이 없다는 사실은 구버전으로 모든 새 초안을 이어 쓸 수 있다는 보장이 아니다. 새 `ReportDraft.research_notice`는 운영 구버전 `49dda2c`의 엄격한 ReportDraft가 모르는 필드다. 새 경고 초안이 생긴 뒤 구버전 이미지로 되돌리면 해당 초안의 보완·서식 준비 등 계약 검증이 거부될 수 있다. 저장된 HWPX 원본·과거 blob을 변경한다는 뜻은 아니며 새 초안 metadata의 호환성 문제다.

롤백이 필요하면 새 보고서 접수를 먼저 멈추고 진행 중 작업·새 notice를 포함한 draft/실행 기록·이미 저장된 HWPX를 보존한다. 새 초안을 유지할 수 있는 호환 버전과 복구 경로를 검토한 뒤 이전 이미지 적용 여부를 결정한다. 호환성을 맞추려고 notice·경고·출처·draft hash를 삭제하거나 다시 쓰지 않는다. 자동 schema downgrade·DB/문서 볼륨 초기화도 하지 않는다. 기존 버전의 동결 preview와 저장 결과를 새 정책으로 소급 변환하지 않는다.
